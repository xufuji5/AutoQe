# 夹具自签的凭据必须与被测服务同源

## 血案

端到端冒烟需要先拿到一个已登录用户。做法是脚本自己签发 token：

```ts
// 夹具：从 .env 读通用密钥
const secret = readEnv('.env', 'AUTH_SECRET')
const token = sign({ sub: userId }, secret)
```

服务端的取值顺序却是：

```ts
// 服务端：专用密钥优先，没有才用通用密钥
const secret = process.env.MINIAPP_JWT_SECRET || process.env.AUTH_SECRET
```

而 `.env.local` 里恰好定义了专用密钥（并且 `.env.local` 覆盖 `.env`）。
于是：**脚本签的 token 服务端永远验不过**，5 条用例整齐地 401。

最贵的部分不是浪费时间，是**结论的方向反了**：报告写着「鉴权接口拒绝合法用户」，
而真实状态是「夹具用错了钥匙」。差一步就去改鉴权中间件了。

同一个坑的第二种形态：夹具连开发服务器用的库/端口/租户都没有对齐 —— 夹具写库 A、
服务读库 B，于是出现「明明插了数据，接口返回空」，然后被归因成「查询条件写错了」。

## 判据纪律

1. 夹具不得自己实现「凭据从哪来」：**import 服务端那个解析器**（导出 `getSecret()` 之类），
   或用一份被双方共用的 `scripts/lib/*-env.ts`。
2. 环境文件加载顺序必须与服务端一致（框架的覆盖顺序是可查的事实，不是约定）。
3. 401/403 的归因顺序：先证明「凭据来源同源」，再怀疑鉴权逻辑。
   一条最小探针（签 token → 打一个只读接口 → 看状态码）比读十遍中间件快。
4. 需要密钥的地方出现**第二份读取实现**，就已经是缺陷；它今天对，是因为两个默认值恰好相同。
5. 时间敏感性同理：夹具与服务的时钟、时区、`now` 来源不同源，会让「窗口类」用例复现不了。

## 反证

```
夹具与服务共用解析器                  → 401 消失
夹具硬编码自己的密钥来源              → 换一台有专用密钥的机器立刻 401
服务端改用另一份兜底顺序              → 共用解析器的用例跟着变（这才是同源）
```

## 怎么问

- 这个 token 是谁签的？它的密钥是从哪个函数拿的？服务端是同一个函数吗？
- 这条用例红了，我先要排除的三种「环境不同源」是什么（密钥 / 库 / 时钟）？
- 如果明天有人在 `.env.local` 里加一个专用变量，这套夹具还绿吗？
