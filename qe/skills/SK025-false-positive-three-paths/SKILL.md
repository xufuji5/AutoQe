# 降误报的三条路，只有第一条是资产

## 血案

一轮全量审计报了 151 条 error。逐条读源码后，没有一条是业务代码写错：

| 成因 | 数量 | 正确做法 |
|---|---|---|
| 判据实现不如它自己的注释 | 36 + 34 + 31 + 13 | 改判据（真的按实参位置 / 回溯赋值 / 删掉日志再看待剩余） |
| 判据跑错仓（客户仓里查客户名） | 64 | 射程自检 → `NotApplicable`（进 skipped，不进 error） |
| 全站维 / 补偿跑批本来跨租户 | 11 个文件 | `platformScope` 声明（有语义依据：对账必须全表扫） |
| 旧守卫在该项目口径不同 | 619 | `downgrades`（error→warn），**读数行必须可见** |

最后只剩 3 条，都是「刻意降级却用了 error 级日志」——值得人看一眼，不是噪音。

## 判据纪律

1. **先问「这条判据有没有做到它自己说的」**，再问「这段代码对不对」。
   前者不成立时，所有读数都是判据的 bug，不是项目的 bug。
2. 射程错了要用 `NotApplicable`（不适用），不要用配置豁免：
   「不适用」和「豁免」在账本上必须是两件事，否则下一个人分不清。
3. 配置降级只许出现在读数行里，且必须带三个数：
   `errors` / `warnings` / `downgraded`。只报 `errors=0` 的报告，与「159 条降级」长得一样。
4. 登记制（`reviewed` / `ownershipReviewed`）**必须强制写理由**，空理由不算豁免。
   否则它会在一周内退化成静音开关 —— 没人记得当初为什么放过它。
5. 改判据之后要能在**干净 checkout** 上复跑：临时措施（本地改动、脏工作树）会让
   「误报降了」变成一句没有证据的话。

## 反证

```
reviewed: { 'a.ts': '理由' }   → 不报
reviewed: { 'a.ts': '   ' }    → 仍报（空理由不算豁免）
downgrades: { 'inv01': 'warn' } 而 guard id 是 'inv01-column-writer' → POLICY_UNKNOWN_GUARD（键写错必须报）
root ≠ packageRoot 的仓里跑「本仓泄漏审计」→ skipped，不是 green
```

## 怎么问

- 这条误报，改完之后「同类写法」还会不会再报？如果还是会，我改的只是这一个文件。
- 这个豁免，半年后有人能说清为什么吗？（理由在配置里，还是在某个人的脑子里）
- 我的报告里，`errors=0` 的背后有没有 `downgraded=619`？

## 附：过严也是缺陷，而且更贵

误报是「判据说错了」，过严是「判据在**正确代码**上判红」。它看起来无害（大不了关掉），
实际代价最高，因为它训练人的动作是**把判据改松**：

> 一条要求「每个 `.tag-*` 修饰类都必须声明字号」的判据，在正确代码上 7/7 全红
> —— 字号写在基类 `.tag` 上、修饰类只管配色，那是**正确**的结构。
> 下一个人的修法不会是「补字号」，而是「把这条判据删掉」。

所以过严的判据要按缺陷处理，处置方向是**判「基类有声明 ∧ 模板挂了基类」**，
而不是放宽到「不判」。同一批实测里还有一条：唯一冲突兜底判据按「行首是不是 `throw`」判纯重抛，
于是把最常见、也最正确的带块条件重抛 `if (!isUnique(err)) { throw err }` 判成了兜底动作 ——
8 个自证例里 1 个在修复后的标准形态上红。

自查三问：

- 这条判据，在**修复后的写法**上是绿的还是红的？（修复后也红 = 它判的不是这件事）
- 它判的是「形态」还是「意图」？意图判不了时，能不能收缩到可判定的子集？
- 如果有人为了让这条绿而改代码，改完的代码更对还是更错？
