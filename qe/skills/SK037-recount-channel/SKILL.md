# 冗余计数必须有重算通道

## 血案

主体记录上挂着 `totalAmount` / `totalCount` / `avgScore`，条目上挂着 `soldCount`。
它们都是**冗余计数**：真值在明细表里，这些列只是为了让列表页不必现场聚合。

维护方式是「写入成功时 `increment`、新增评分时重算平均值」。问题不在写法，在于：

- 夹具 / 种子 / 迁移回填 / 手工修数**都不走那条增量路径**；
- 一旦有一步没走，计数就永久偏离，而且**没有任何命令能把它算回来**；
- 守恒门禁（「计数 == 源表聚合」）于是每一轮都红，红的条目还每次不一样；
- 人很快学会「这几条是已知红」——**门禁从此变成噪音**。这比没有门禁更贵：
  以后真的坏掉时，没人再看得懂。

这不是代码缺陷，是**能力缺口**：系统缺一个「从源表重算」的入口。

## 判据纪律

1. 任何 `total* / *Count / *Sum / avg*` 列，都必须能回答：**哪条命令能把它从源表算回来？**
   答不上来，它就不是缓存，是第二个真相源。
2. 守恒类门禁（计数 vs 源表聚合）必须与**重算通道同时存在**。只有门禁没有通道 ⇒
   门禁的唯一作用是制造噪音；只有通道没有门禁 ⇒ 没人知道什么时候该跑。
3. 重算脚本必须**与门禁口径同源**：同一条 SQL 谓词（哪些状态算「有效」、哪些记录算「已确认」）。
   两边各写一份谓词，是「门禁绿了但数还是错」的标准成因。
4. 重算脚本默认**干跑**（只打印差异：表名 / 行 id / 现值 / 应有值），`--apply` 才写。
   干跑的输出就是下一次对账的证据。
5. 增量写与重算并存时，先说清**谁赢**：重算跑完后的增量写必须仍然正确，否则下一次又漂。

## 修复形态

```ts
// 干跑：只读，逐条列出「现值 ≠ 应有值」
await prisma.$transaction(async (tx) => {
  const rows = await tx.$queryRaw`SELECT owner_id, COUNT(*)::int AS n FROM detail_rows ... GROUP BY 1`
  // 与主体上的冗余计数比对，输出 { table, id, column, current, expected }
})

// --apply：只写差异行，仍在同一事务里，末尾打印 Σ 改动行数
```

配套门禁要能**自报分母**：`777 列 → 752 有写入 + 25 零写`，而不是只报「有 25 个问题」。
要人猜分母的读数，就是下一轮对账的税。

## 反证

```
故意把某个主体的 totalCount 改成 0，跑干跑    → 必须报出这一行（现值/应有值）
跑 --apply 后复跑守恒门禁                     → 必须绿
再让并行批次写入一次                           → 会重新漂（这是设计缺陷，不是脚本坏了）
只有门禁没有重算通道                           → 每一轮都红，且红的条目会变（噪音化）
```

## 怎么问

- 这个计数列，上一次被正确维护是什么时候？谁证明的？
- 如果它现在偏了，我该跑哪条命令修回来？（答不上来 = 缺能力，不是缺数据）
- 门禁与重算脚本用的是同一个「有效行」谓词吗？
