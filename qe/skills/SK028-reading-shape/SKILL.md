# 读数形状

## 真实形态

```ts
const rows = await prisma.$queryRaw`
  SELECT COUNT(*)::int, COUNT(*)::int FROM ...`
const [cur, base] = Object.values(rows[0])   // 以为拿到两个数
```

PostgreSQL 给**没有别名**的聚合列起的名字就是函数名（`count`）。两列同名，
行对象化（Prisma 行对象、`JSON.parse`、任何按列名建对象的驱动）时后一个覆盖前一个。
SQL 合法、类型合法、对象非空——**它长得像成功**。于是「0 / 19」显示成「19」：
分母没了，只剩分子，而那个数看起来更合理，所以没人质疑。

## 为什么这是「证据不足」而不是「算错」

对账的结论依赖读数，读数的键依赖驱动行为。错不在算，在**这一列根本取不到**。
更糟的是错的方向常常是「更像真的」那一侧——丢分母、丢 0 值、丢 null 分组。

## 三条修法（按优先级）

1. **每一列显式 `AS` 一个不同的名字**（唯一根治）；
2. 读数**自带分母**，且写进 detail 的**最前面**——很多断言/日志会截断尾部（如 `slice(0, 200)`），
   写末尾等于没有；
3. 不要指望 `Object.values` 的**位置**：覆盖发生在更早的一层，键都不存在时位置信息已经丢了。
