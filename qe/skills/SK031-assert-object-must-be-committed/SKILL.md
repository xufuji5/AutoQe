# 判据的对象必须是能被提交的东西

## 真实形态

判据要「证明文档里引用的素材都在」，于是断言：

```ts
assert('参考图存在', existsSync('新设计方案/参考页面/a.jpg'))
```

问题：那个目录在 `.gitignore` 里。**本机恒绿**（文件就在），**干净克隆恒红**（文件根本不会被 checkout）。
这不是判据太严，是它问错了对象——它问的是「我这台机器上有没有」，却把它当成「仓库完不完整」。

## 为什么它会长期隐藏

- 单机开发时永远绿，没人会去质疑一条绿判据；
- 第一次在 CI 上红，会被当成「CI 环境问题」而不是「判据写错了」；
- 修法常见错向：把路径加进白名单豁免——于是判据从此什么都没判。

## 修法

把「存在」拆成两问，分别判：

1. **磁盘存在 ∧ 不被忽略**：才是「仓库完整」的证据。忽略与否去问 git
   （`git check-ignore --stdin -z`），**不要手抄忽略规则**——分层规则手抄即过期；
2. 被忽略的素材**单独进读数**（「有 3 个引用指向不入库素材」），而不是混在红里。

## 自省

- 这条断言在干净克隆里还能成立吗？我怎么知道的（跑过还是猜的）？
- 它要求的对象，是「代码/文档」还是「我本机的某种状态」（时间、随机数、环境变量、本地缓存、未入库素材）？
- 这条红如果出现，第一个反应是去修代码，还是去改判据？后者说明判据本身有问题。
