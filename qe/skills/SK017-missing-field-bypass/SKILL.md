# 字段缺失绕过判据

## 血案（同一个陷阱在一天内踩了两次）

**读侧**：升级门槛写的是

```ts
if (stat.reviewed === 0) return { ok: false, why: '还没有人工复核记录' }
```

旧账本里根本没有 `reviewed` 这一栏 → 读到 `undefined` → `undefined === 0` 为 **false**
→ 门槛被跳过 → `doctor` 把 **8 条规则全部列成「可升级」**。而实际上一处都没复核。

**写侧**：`recordReview` 里

```ts
reviewed: prev.reviewed + opts.reviewed     // undefined + 7 = NaN
```

打印出 `reviewed NaN`。而 `NaN` 在任何比较里都是假 —— 于是「已复核」永远不成立，
且**不抛任何错误**。读数的破坏是静默的。

## 为什么这类 bug 一定会有

**新加字段 · 旧数据**这个组合在任何有持久化状态的系统里都会出现一次。
判据侧尤其危险，因为判据的默认行为通常是「不满足条件就放行」还是「不放行」——
写反了就是恒真。

## 两条硬规矩

1. **布尔化判断，不要用等值比较**：`if (!stat.reviewed)` 而不是 `=== 0`。
   对 `undefined / null / 0 / NaN` 一律成立，正好是「没有」的语义。
2. **数值累加必须兜底**：`(prev.x ?? 0) + n`。别指望「字段总是存在」。

## 反证（缺了这个就等于没修）

```
跑够轮数 + 已复核 + 0 争议  → 可升级
没复核过                    → 不许升级
旧账本缺 reviewed 字段      → 不许升级     ← 这一条才是本血案的判据
有一处争议                  → 不许升级
轮数不够                    → 不许升级
```

再补一条写入侧的：

```
旧账本 + recordReview(7) → reviewed === 7（不是 NaN）
```

## 怎么问

- 这个判据读的字段，第一次写入是什么时候？在它之前的数据长什么样？
- 我是用「等于某个值」判「没有」，还是用「假值」判「没有」？
- 如果这里静默变成 NaN，谁会看到？（答：没人 —— 所以要自证）
