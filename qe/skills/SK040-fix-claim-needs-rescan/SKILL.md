# 修复者宣布的「已解决」只是主张

## 血案

一轮修复下来，自建判据 17/17 全绿、全量回归也绿，于是宣布清零。
随后用一套**完全没参与修复**的外部规则集复扫，撞出：

- 1 条**真缺陷**（业务写入口在并发下把唯一冲突冒成 500，调用方重试即死循环）；
- 3 条**判据自身的缺陷**（三条红全部落在夹具脚本里：写死依赖目录取 CLI，
  干净 checkout 下零输出被读成「被测对象失败」）。

第一条最值得记：它从来没被自测发现过，因为**写判据的人和写实现的人有同一个假设**
（「这个入口是幂等的，重复调用不会出错」）。这个假设同时决定了实现和判据，
所以判据再密也撞不出来。

第二条同样重要：外部引擎的红**大部分指向判据而不是业务代码**。
这说明「换一套判据」的价值不只是找 bug，还包括照出自己判据的盲区。

## 判据纪律

1. 宣布「已解决」需要**三方证据**里至少两方：①外部/独立判据复撞无红；②真库/真链路探针；
   ③线上或历史数据对账。只有自建判据绿，只算「主张」。
2. 修复与判据不得由同一个假设驱动：判据要能回答「**什么情况下我会红**」，
   而那个情况必须是修复**之前**真实存在的形态（不是修复后代码的形状）。
3. 复扫出的红先分类再动手：本批引入 / 存量 / 并行批次 / **判据误报**。
   把判据误报当成业务缺陷改代码，是这类审计最贵的一种浪费。
4. 复扫读数要问「它看的是哪棵树、哪个集合」：工作树绿 ≠ HEAD 绿；
   一条「0 命中」的判据要先证明它扫到了对象（自报分母）。
5. 复扫用的规则集要能独立升级：判据也是代码，它自己的 bug 不会因为它绿而消失。

## 反证

```
自建判据全绿 + 外部引擎 3 红            → 宣布「已解决」为时过早
外部引擎红里 3/3 在夹具                 → 判据侧缺陷，业务可能没问题
删掉修复（把 catch 移回事务内）再看自建判据 → 若仍绿 ⇒ 判据没有承重能力
```

## 怎么问

- 这条「已解决」的结论，是哪个判据给的？它参与过修复吗？
- 如果我把修复回滚，这条判据会红吗？（不会红 = 它证明不了这件事）
- 复扫的 0 命中，是「真的没有」，还是「它没看那里」？
