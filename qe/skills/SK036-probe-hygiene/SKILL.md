# 探针卫生：证据留下、污染带走

承重反证（绕过业务写口、裸并发插同一行，证明「绿来自约束不是时序运气」）是最值钱的一类探针，
也是最容易自己骗自己的一类。它有两个反复出现的坑。

## 坑一：错误身份认错，断言恒不成立

```ts
// 第一版：认 SQLSTATE
const dup = results.filter((r) => r === '23505').length
suite.assert('7 条被唯一索引挡住', allowed === 1 && dup === 7)
```

实测 `dup === 0`，而数据库**确实**挡住了 7 条。原因是 `$executeRawUnsafe` 把 PG 错误
统一包成 Prisma 的 `P2010`，`err.code` 拿不到 `23505`。

改成读 `err.message` 找 `duplicate key` 又会踩第二个雷：**message 受服务端 locale 影响**
（中文库返回「重复键违反唯一约束」），换台机器结论就反了。

跨 locale 稳定、跨 Prisma 版本稳定的只有一样东西：**约束名**。Prisma 的 `P2010` message 里
会带上 `constraint "xxx_key"` / 索引名 —— 认这个名字才是可复现的判据。

```ts
.catch((e) => (String(e?.message).includes('ledger_ref_type_ref_id_action_key') ? 'IDX' : 'OTHER'))
```

纪律：
1. 断言「被约束挡住」时，认**约束名/索引名**，不认 SQLSTATE、不认本地化的 message、不认 `err.code`。
2. 拿不到约束名时，判据应当**失败**（红），不许退化成「计数为 0 就算过」。
3. 反证应当能报出**丢的是哪一条**（`missing: ["c92a3ac7"]`），否则下次对账还得重来。

## 坑二：DDL 在事务外，ROLLBACK 管不着

探针为了造场景常会 `CREATE EXTENSION`、`CREATE INDEX`、`CREATE TEMP TABLE`。
前两个是**数据库级副作用**：写在 `$transaction` 里也一样持久（PG 的 DDL 是事务性的，
但 `CREATE EXTENSION` 的副作用与并行建索引、以及「事务外执行」的写法都会留下来）。

留下的后果不是「多一个对象」，而是**改变了共享事实**：下一个据此判断「本库是否已具备该能力」
的判据、迁移、乃至别人手工执行的 `EXPLAIN` 全部基于一个假前提。

纪律：
1. 探针的每一条建对象语句，都必须在 `finally` 里有对应的 `DROP`；或者整段写在事务里并
   **无条件** `ROLLBACK`（不是只在不通过时回滚）。
2. 「证据留下、污染带走」说的是结论与读数，不是对象与数据行。
3. 跑完探针要能回答一句：**这条探针跑完之后，库里比跑之前多了什么？** 答不上来就别跑。

## 反证

```
断言认约束名 + 裸并发 8 路            → 1 成 7 撞，读数与结论一致
断言认 '23505'                        → 恒 0，判据红（它红得对，但理由错）
删掉业务写口的 catch 后重跑            → 必须红（否则反证没有承重）
CREATE INDEX 写在事务外且没 DROP      → 污染残留（下一次扫库能看到）
```

## 怎么问

- 这条断言凭什么认出「是约束挡的」？换一台中文库、换一个 Prisma 版本还成立吗？
- 探针建的东西，`finally` 里删了吗？没有 `finally` 的话，中途抛错时谁来删？
- 这条探针红了，能指出是哪个键、哪一行、哪一条丢了吗？
