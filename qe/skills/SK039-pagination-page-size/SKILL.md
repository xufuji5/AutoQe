# 分页判据：不重只是半个判据

## 血案

游标分页最常见的判据是「第一页和第二页没有重复」——它只证明**不重**，
而漏行（`last` 那条被跳过）在读数上表现为「页数少了一点」，不重判据**全部通过**。

更隐蔽的是它对页长极其敏感：

| 页长 | 结果 |
|---|---|
| 1 / 3 / 5 | 丢 1 条 |
| 2 / 4 / 6 | 全对 |

原因：缺陷只在「并列行正好落在页边界」时触发。那对并列行在整体排序里的索引是 14，
只有当页长整除 15 时，游标才落在它们身上。**用默认页长跑一遍没问题，不构成证据。**

第二层坑在游标键本身的精度：

```ts
// SQL 侧：全精度
ORDER BY (-EXTRACT(EPOCH FROM deadline)) ASC, id ASC
// 应用侧：整秒
const cursor = -Math.floor(row.deadline.getTime() / 1000)
```

行比较在**键值这一层**就失败了，根本轮不到 `id` 兜底。两端必须是同一个量纲：
要么都整数毫秒（`-FLOOR(EXTRACT(EPOCH FROM deadline) * 1000)` ↔ `-date.getTime()`），
要么都是同一个 `numeric`。传参时也别让驱动把 float8 转成 numeric 再截断。

## 判据纪律

1. **两个方向都要判**：逐页并集 == 宽页并集（不漏）∧ 逐位序一致（不重且顺序稳定）。
2. **扫页长**：至少 `[1, 2, 3, 5, 7]`。只在默认页长上跑，等于没测。
3. 夹具里要**故意造并列键**（同 deadline 的两三行），否则边界永远撞不到。
4. 游标键两端同精度、同量纲；断言要写「取不到的那条 id 具体是哪个」，
   能报 `missing: ["c92a3ac7"]` 才算可复现。
5. 分页判据与排序判据分开：顺序对了不代表不丢，不丢也不代表顺序对。

## 反证

```
把游标从「大于」改成「大于等于」        → 判据必须红（重复）
把游标改成「严格大于次边界」            → 判据必须红（漏行）
页长 1/3/5 各跑一遍                     → 漏行必须在至少一个页长上暴露
游标键改成整秒（SQL 侧仍全精度）        → 必须红（键值层就错）
```

## 怎么问

- 这条判据能证明「一页都没有丢」吗？还是只证明了「两页之间没有重复」？
- 我跑过几个页长？默认页长会不会正好躲开边界？
- 游标值两端是同一个精度吗？谁把它截断的？
