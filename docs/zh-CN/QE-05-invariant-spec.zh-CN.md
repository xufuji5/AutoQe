## 一、为什么把不变量放进设计规范（而不是测试规范）

缺陷的处置成本随**发现层级**上升，而层级在**设计时就已经定死**：

| 层级 | 在哪拦 | 拦得住什么 | 拦不住什么 | 本工具箱载体 |
|---|---|---|---|---|
| L0 类型 / schema | 写代码时 | 拼错键、漏字段、类型混用 | 语义错误、缺写入者 | TypeScript、`prisma/schema.prisma` |
| L1 DB 约束 | 落库时 | 唯一性、非空、外键、范围 | 跨行恒等式、时序 | 迁移里的 unique / partial unique / CHECK / FK |
| L2 契约 | 调用边界 | 请求响应形状、错误码语义 | 内部状态机、并发 | 目标仓错误码模块（如 `lib/apierror.ts`） |
| L3 不变量判据 | 提交时（静态/读数） | 「某类事实根本不成立」的全仓扫描 | 运行时行为、外部系统 | `qe/guards/*`、`npm run qe` |
| L4 冒烟 / e2e | 跑起来时 | 链路行为、竞态、跨模块时序 | 「没人写过的路径」 | 目标仓 e2e / 冒烟脚本 |
| L5 人工巡检 | 上线后 | 判断、取舍、外部世界 | 概率为 0 的执行者 | runbook、周审计 |

三条硬规矩：

1. **能用 L1 表达的，绝不下放到 L3。** DB 约束是唯一「不可能违反」的层——它不依赖任何人记得跑门禁。
   写不出 L1 约束时，必须在设计稿里写明「为什么约束层表达不了」，否则视为漏设计。
2. **能用 L3 表达的，绝不留给 L5。** 人工巡检是概率为 0 的执行者：本仓案底＝死信告警读
   `status='failed'`，而全仓**没有任何地方写它**，两条运维通道恒空数月，靠的正是「总会有人看」。
3. **层级定死之后不许随实现漂移。** 同一个事实在 L0/L1/L2 各写一份判定＝漂移（QE-04第一类）。
   判定单源的位置由本规范指定，写在别处即视为副本。

## 二、什么算「不变量」（四条准入）

不变量不是「重要的规则」，是**能被机械判定为真/假的全称命题**。四条缺一不进册：

| # | 准入条件 | 不满足时的样子 |
|---|---|---|
| I1 | **可机械判定**：要么能扫源码，要么能查库，两者都不行的不算 | 「页面要好看」「代码要清晰」 |
| I2 | **反例可构造**：说得出一条必然违反它的输入 | 「不应该出错」——构造不出反例，说明它没内容 |
| I3 | **与实现无关**：说的是业务事实，不是某个函数怎么写 | 「必须调用 `settle()`」——那是实现约束，会随重写失效 |
| I4 | **失效有业务后果**：说得出「破了会怎样」 | 「字段应该有注释」——破了没人受损 |

**不合格的四类，直接退回**：风格偏好／无阈值的性能目标（「要快」→ 写成 P95 阈值才合格）／
一次性检查项（只做一次的动作不是不变量，是任务）／带「应该」「尽量」的软句。

合格的写法示范：`每一列要么有写入者，要么不存在（没有第三种状态）`——全称、可扫、有反例
（新增一列不接线）、后果明确（列永为 NULL，读侧恒空）。

## 三、从需求到判据的路径（需求评审五问）

任何新功能、新字段、新状态、新入口，**立项稿必须附这五问的答案**（答不出＝需求没想清，不是判据没写够）：

| # | 问题 | 答不出时的处置 |
|---|---|---|
| Q1 | 这个功能**违反**了哪几条已有不变量？（逐条列 INV 编号） | 违反 → 先改设计，不许靠 `open` 把它绕过去 |
| Q2 | **新增**了哪条不变量？没有新增的话，为什么？ | 无新增＝要么功能没有约束（多半是漏想），要么约束藏在实现里 |
| Q3 | 在哪一层拦（L0–L5）？为什么不在更低层？ | 见 §一 三条硬规矩 |
| Q4 | 有没有**不可逆动作**？ | 有 → 必须走 §四，设计稿给读数与撤销动作 |
| Q5 | **反例**是什么？ | 写不出 → I2 不成立，这条不算不变量 |

Q1 的执行方式：`qe/registry/registry.ts` 里的 27 条是当前全集，逐条读 `statement` 与 `defectClasses`，
把可能被这次改动破坏的列出来写进立项稿。**这是设计动作，不是检查动作**——在写代码前做，
和写完代码后补一份「检查表」是两件事。

## 四、不可逆动作的设计位（本规范最硬的一节）

「不可逆」指**事后无法用代码修复**的动作。本仓已确认的四类，各自的设计期义务：

| 类型 | 不可逆在哪 | 设计期必答 |
|---|---|---|
| **删列 / 删表 / 改字段语义** | 列能加回，数据加不回；语义改了旧数据变成谎 | ①「该列全空且表有行」的读数（空表读数不算证明）②删前是否已无消费方（含文档与断言）③走迁移批呈批五问 |
| **数据回填** | 回填只能取「当前值」，而当前值≠历史事实 | 回填值是被**编造**的，必须落「快照列 + 采集时点」而不是覆盖原字段 |
| **预扣 / 冻结 / 物化列** | 物化即复制，撤销有窗口 | **两条时效必写**：放行多久生效、撤销多久生效（后者是风控问题，不是性能问题）；物化列的维度语义（含哪些维度、是否 entry-only）写进列注释 |
| **外呼（短信 / 推送 / 打款）** | 发出即不可撤回 | 幂等键 + 可撤销窗口 + 失败可见（失败必须落账，不许只进日志） |
| **迁移链** | 已应用的 `migration.sql` 一字节都不能改（P3008） | 改字段一律手写新迁移；schema 与迁移链的对象集合必须零漂移 |

判据形态：每条不可逆动作的不变量，**必须有一个「前置读数判据」**（做之前能不能做，靠读数回答，
不靠人回忆）。参考实现：`test:invariants-columns` 的 `decision` 组要求「判删的列必须有该列全空且
表有行的读数」，`volume-gate` 组要求「每条待裁决列都有读数档」——**读数缺失本身就是红**。

## 五、判据形状纪律（D1–D12）

「写了判据」和「写了有效判据」的距离，本仓交过学费。以下十二条，每条都带案底；
断言的取证等级以 [QE-03 §4.1](QE-03-project-audit-and-release-gate.zh-CN.md) 为准（E0 只是线索，不得单独判级），不在此重复。

| # | 纪律 | 案底 / 理由 |
|---|---|---|
| D1 | **禁空集恒真**：判据在空集/空表上恒真＝假绿；造数/前置本身也要断言 | 冒烟在空表上断言「零写入列 = 0」永远绿 |
| D2 | **反证注入**：新判据必须先用「旧实现」跑一遍，确认它必红 | 判据放宽（扩射程）本身就是假绿入口，放宽前必须有反证样本（如「只 CREATE SCHEMA 不 DROP 仍须红」） |
| D3 | **静态判据先剥注释**：命中词在注释里不算实现 | 否定型断言裸 grep 会被自己的注释喂绿 |
| D4 | **单源**：判据/口径/阈值/文案/注释只留一份，镜像必须有逐输入比对守卫 | 注释写「默认 true」而迁移是 NULL——注释也是单源的一部分 |
| D5 | **一个守卫只打一行 `GUARD_SUMMARY`**：业务读数走 `GUARD_DETAIL` | 两行会让汇总把同一守卫数两次，数字从此不可信 |
| D6 | **ratchet 只准变少**：新增违规不许直接进 baseline，只能修或删 | baseline 是存量债账本，不是豁免开关；「塞进 baseline」＝把新债洗成旧债 |
| D7 | **环境/时段敏感读数不进 CI**：用非 `test:` 前缀别名 | 库内读数随环境变，把数字写进 CI 等于把环境差异变成假红 |
| D8 | **清理必须在 `finally`**；退出用 `exitCode` 不用 `process.exit()` | `catch` 覆盖不了 fatal，`process.exit()` 会跳过 `finally` |
| D9 | **差分断言在噪声 ≥ 信号时撤掉，留观测** | 别调阈值凑绿——调阈值是让判据适应缺陷 |
| D10 | **射程必须声明盲区**：判据文件头写「本判据看不见什么」 | 不声明盲区，读者会以为它覆盖了全部 |
| D11 | **结论必须有期限，执行必须退场**：裁决带 `decidedAt`/`dueBy`，超期未执行即红；执行完从账本移除 | 「有结论」曾被当成「已处置」，`decision: 'delete'` 可在 baseline 里永久躺着而门禁常绿 |
| D12 | **观察器三约束**：不抛 / 节流 / 稳定指纹；熔断在内存须落痕 | 观测代码抛错会把主流程带下去，等于制造新故障 |

## 六、生命周期（三态 + 复审 + 到期）

不变量不是「立了就完事」，它有自己的生老病死。**状态单源=`registry.ts` 的 `status` 字段**：

| 状态 | 含义 | 准入义务 |
|---|---|---|
| `enforced` | 有守卫且已在闸内，违反即红 | 守卫别名必须可寻址（`test:invariants` 的 `addressable` 组） |
| `partial` | 有守卫但射程不全 | 必须写 `gap`（差在哪）与 `next`（怎么补），不许只写「部分覆盖」 |
| `open` | **当前守不住** | 必须写 `openReason`（为什么守不住 / 谁能裁）+ `revisitBy`（复审日期） |

三条硬规矩：

1. **守不住的不许隐身**：不许因为「没有判据」就从册子里删掉这条。`open` 有账不算红，**无账即红**
   ——这是 `test:invariants` 的核心判据。
2. **复审窗口 ≤ 90 天**：`revisitBy` 超窗必须重定，且重定时要留「复审过」的痕迹（改一个字也算，
   说明有人真的读了）。
3. **状态只能靠证据升级**：`open → partial → enforced` 每一步都要有守卫别名支撑，
   不许「我们觉得差不多了」直接改 `enforced`。

**新增一条的正确顺序**：先在 `registry.ts` 登记（哪怕 `status: 'open'` + 理由）→ 再写守卫 →
最后改 `status`。反过来（先写代码后登记）会让「这条规则存在」变成口头事实。

## 八、三层落地清单

| 层 | 动作 | 判据 |
|---|---|---|
| **立项** | 五问（§三）+ 不可逆动作义务（§四）+ 接缝协议（QE-06） | 立项稿含 INV 编号与反例 |
| **开发** | 新增/修改的不变量先进 registry；判据遵守 D1–D12 | `test:invariants`（可寻址/必带理由/复审窗口） |
| **提交 / 发版** | 门禁全跑（`test:` 前缀自动入闸） | `run-all-tests` 全绿 + `tsc --noEmit` 0 |

**禁止的动作**（历史上都发生过）：靠 `--no-verify` 跳过钩子／把新违规塞进 baseline／
把「没有判据」写成 `enforced`／在文档里维护第二份条目清单／把环境读数写进 CI 断言。

## 九、反面清单（不该做成不变量）

做不变量有成本（写判据、维护 baseline、每次改动都要跑）。以下四类不该进册：

1. **样式与文案偏好**——没有业务后果，属于 §二 I4 不成立。
2. **可选优化**——「可以更快」不是约束，除非给出 P95 阈值与测量方法。
3. **需要人判断的措辞**——「文案要得体」无法机械判定。
4. **一次性检查项**——发版前该跑一次的脚本是任务清单，不是不变量。

判断口径：**问「违反它会造成什么损失，谁受损」**。答不出受损方，就不该进册。
