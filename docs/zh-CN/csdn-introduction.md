# 当 AI 成为主力程序员，质量该怎么管？我开源了 AutoQe：一套「不变量优先」的 AI 编程质量工程

> 项目地址：https://github.com/xufuji5/AutoQe （MIT，欢迎 Star / Issue / PR）
> 技术栈：Node.js ≥ 22.18、TypeScript 5.9、Prisma 5/6、Next.js、Zustand

## 一、一个很多团队都遇到过的场景

AI 写代码的速度，已经超过了人审代码的速度。

一个中等规模的业务系统，两三个月就能堆出几十个路由、上百个 server action、几百个字段。功能都能跑，演示也没问题。但上线之后，问题开始以另一种方式出现：

- 某个字段全库没人写，界面却一直在读，永远显示空值；
- 某个枚举值定义了、类型也通过了，但没有任何一条路径能产生它；
- 接口文档写着「必须传幂等键」，代码里没有一处校验；
- 两个模块各自实现了一遍同一件事，改了一边，另一边悄悄过期；
- 上一次修过的 bug，下个迭代换个入口又回来了。

这些问题有个共同点：**它们不会报错，只会静默地错**。测试跑绿，构建通过，代码评审也挑不出明显毛病——因为缺陷不在某一条路径上，而在「结构」里。

## 二、为什么「多写测试」追不上 AI 的缺陷

测试是枚举：一条用例验证一条路径。而 AI 的缺陷是结构性的：它会在模块接缝、边界条件、状态迁移、并发窗口里成批出现。

枚举永远追不上结构。你补 100 条用例，下一批需求又会带来 100 个新的结构面。

所以这个项目的出发点只有一句话：

> **质量 = 约束密度。不变量 > 用例。**
>
> 用例问「这条路径对不对」，不变量问「这件事是否恒成立」。

先把「什么永远不能发生」写成机器可判的约束，再写业务逻辑，最后才跑测试。顺序反过来，就只能在缺陷发生之后追着跑。

## 三、这个项目是什么

**AutoQe** 是一套面向 AI 辅助开发的质量工程工具箱，不是一个业务框架，也不绑定某个产品。

它把「不变量」变成四样可以落地的东西：

1. **注册表**：所有不变量条目登记在一个 TypeScript 单源里，禁止在文档里维护第二份真相；
2. **守卫**：每条可自动化判定的不变量，对应一个静态扫描守卫；
3. **坏样本**：每个守卫都必须对一份独立构造的错误代码「见红」，先红后绿；
4. **棘轮**：缺陷计数基线只准下降，任何回归直接让 CI 失败。

当前仓库自带 27 条不变量（enforced 10 / partial 5 / open 12）、9 个守卫、19 个坏样本自证，以及一套可复制的项目体检作业单。

## 四、三个关键设计

### 1. 不变量单源，文档只写方法

条目的唯一真相在 `qe/registry/registry.ts`。文档（QE-00 ~ QE-09）只讲方法、口径和指针，不复制条目清单。

这样做的好处很直接：不会出现「文档说 15 条、代码里 27 条」这种对不上账的情况。任何一条不变量都必须写清楚：违反哪条、在哪一层拦（L0–L5）、有没有不可逆动作、反例是什么。

### 2. 坏样本先红后绿，AI 自测不单独采信

一个守卫写完就报绿，是最典型的假绿。所以每个守卫上线第一天，必须能在一份**独立构造的坏样本**上失败，并且失败原因必须是预期的那个。

仓库里的 `qe/fixtures/` 就是这些坏样本：零写列、零读列、死枚举、幽灵规则、空转闸、越界客户端导入、无 partialize 的 Zustand 持久化……每个都有对应的自测用例。

`npm run qe:selftest` 会同时检查两件事：坏样本必须红，好样本必须绿。假红和假绿同罪。

### 3. 棘轮只降不升，修过的 bug 不许回来

`qe/ratchet.json` 记录每类缺陷的计数基线。规则只有一条：

- 数量下降：允许，自动更新；
- 数量上升：CI 失败，退出码 1。

这条机制解决的是「修完又犯」——不是靠人记住，而是靠基线卡住。新增违规永远不许塞进基线。

## 五、五分钟跑起来

```bash
git clone https://github.com/xufuji5/AutoQe.git
cd AutoQe
npm install
npm run qe:selftest   # 19 个坏样本自证
npm run qe:ci         # 类型检查 + 自证 + 守卫 + 报告
```

真实输出（本仓当前读数）：

```text
SELFTEST_RESULT cases=19 passed=19 failed=0 status=green
QE_RESULT guards=9 errors=0 warnings=0 skipped=0 status=green
RATCHET status=ok regressions=0 improvements=0 tracked=0
METRICS invariants=27 enforced=10 partial=5 open=12 enforcedCoverage=100% skipped=0
```

常用命令：

| 命令 | 作用 |
|---|---|
| `npm run qe` | 跑守卫并比对棘轮基线 |
| `npm run qe:list` | 列出全部不变量及其状态 |
| `npm run qe:selftest` | 坏样本反证（假红假绿都会失败） |
| `npm run qe:report` | 生成带日期的健康指标快照 |
| `npm run qe:ci` | 提交前完整门禁 |

## 六、拿它体检你现有的项目

这套东西更大的用途，不是从零新建项目，而是**给一个已经跑起来的项目做上线前体检**。

`QE-03` 给出了一份与业务无关的作业单，分五个阶段：

- **S0 事实基线**：构建、启动、迁移、环境变量、入口总数先数清楚；
- **S1 快扫**：15 项快速检查，先找出「一眼就能看到」的问题；
- **S2 深挖**：沿七条主线（入口、鉴权、数据、并发、前端状态、外部集成、运维）逐项核对；
- **S3 定级**：按 P0–P3 定级，每条结论必须带证据等级（E0–E3）；
- **S4 上线判定**：12 道 Gate 逐条给结论，输出「可上线 / 有条件上线 / 不可上线」。

最后产出六份固定文件：事实基线、入口清单、扫描记录、Bug 台账、上线判定、缺口吸收计划。前五份不齐，不允许给出上线结论。

## 七、它刻意不做什么

这一点需要说清楚，避免误用：

- **它不是「升级包」**。如果目标项目已有更严格的守卫或流程，原样保留；本工具只补它没想到的问题，不做整体替换。
- **它不把「跳过」当「通过」**。当 schema 或源码适配器配置为 `none` 时，相关守卫输出 `skipped`（黄色），绝不报绿。
- **它不采信 AI 自己的结论**。没有可寻址证据（commit / 守卫读数 / 台账行）的「已完成」，一律不算完成。

## 八、适合谁

- 用 AI 大量写业务代码，但苦于「修完又犯」的团队；
- 技术栈是 Next.js + Prisma + PostgreSQL + Zustand 的前后端项目；
- 需要在两周内给一个存量系统做上线前体检的技术负责人；
- 想给团队建立「先立约束、再写业务」协作协议的小团队。
