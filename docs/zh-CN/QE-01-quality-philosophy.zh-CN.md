# QE-01 · AI Coding Quality Handbook (General Edition v1.0)

> Chinese edition of [QE-01-quality-philosophy.md](../../QE-01-quality-philosophy.md).

> 适用对象：以 AI 为主要编码力量的中小团队（1–5 人 + AI），典型系统为带资金、状态与审计流的业务系统。
> 使用方法：第五至九章是顺序手册（按序执行）；第八章不变量库与附录 B 判例集是查表材料；每个新仓从第十章体检开始。
> 本手册全部判据均来自真实生产仓的付费学费（2026 年实测），不是理论推演。

## 〇、核心命题：质量 = 约束密度

### 0.1 AI 缺陷物理学

AI 生成代码的优化目标是「局部合理」——编译过、类型过、与 prompt 字面一致。它不具备三种能力，而缺陷恰好从这三种缺失里长出来：

| AI 缺失的能力 | 缺陷签名 | 典型实例 |
|---|---|---|
| 没有全局不变量概念 | 键在 API 合同里、**零发送者**；列在 schema 里、**零写入者** | 契约键 `round/isRetest` 零收集面；逐签人四列活表死列 |
| 偏向静默成功（`catch`/`??` 兜底比抛错「看起来更稳」） | 查询炸了显示成空态；**缺省即判定值** | 附件缺列 500 被吞成「未放行」；`?? "pass"` 把批量核对写成默认合格 |
| 只接快乐路径 | 死分支、假入口、整表未落地 | 「确认补录」按钮指向不存在的通道；整改表建表后零引用 |

**推论一：测试是枚举，AI 的缺陷是结构性的——枚举永远追不上结构。** 每加一条 e2e 测一条路径，AI 在第 101 条路径上翻车。在缝隙上堆测试，只是把水扫得更勤。

**推论二：不变量 > 用例。** 用例问「这条路径对不对」（测一次少一个）；不变量问「**这个系统里这件事是否恒成立**」（立一次，管全部路径、全部未来代码、包括 AI 明天写的）。

### 0.2 错误成本层级（让错误在越便宜的层爆炸）

| 层 | 抓什么 | 相对成本 | 特征 |
|---|---|---|---|
| L0 类型/Schema | 非法状态不可表达 | 1× | 被 AI 用 `as`、`??`、强转绕过 = 层破 |
| L1 数据库约束 | RLS、FK、唯一索引、触发器 | 5× | 对业务表有效≠对全部表有效 |
| L2 契约单源 | API 键集、错误码、枚举、提交体 | 20× | 缝隙高发区（册↔码↔提交体三面） |
| L3 不变量守卫 | 一类缺陷一个判据 | 100× | 必须自带反证，否则是纸面 |
| L4 e2e 流程 | 端到端冒烟 | 1000× | 只验主链路，不重复守卫已挡的 |
| L5 人工审查 | 语义、视觉、业务判断 | ∞ | 登记盲区，不假装没有 |

**质量控制的全部工作，就是把缺陷从 L4/L5 拽回 L0–L2。** 测试不会变少，但会变便宜。

## 一、五层闸门法总览

| 闸门 | 核心问题 | 产出物 | 验收线 |
|---|---|---|---|
| **① 设计闸** | 这句话机器能验吗？ | 不变量注册表 + 方向裁决记录 | 每条不变量有判据+坏样本，缺一不许标 enforced |
| **② 架构闸** | 洞会长在哪个缝？ | 表所有权矩阵 + 依赖方向图 | 不存在「两边一起缺」的结构 |
| **③ 栈闸** | 这门技术能约束 AI 吗？ | 选型判据表 + 边界生成器 | 边界代码零手写 |
| **④ 规范闸** | 规范是生成源还是参考材料？ | 每模块规范四件套 | 规范可直接喂代码生成，写完不再对账 |
| **⑤ 测试闸** | 测性质还是枚举路径？ | 守卫族 + 冒烟 e2e + 盲区登记 | 守卫三态齐全，假红假绿同罪 |

**纪律：一层答不出自己的核心问题，后面四层全是沙上建塔。** 顺序就是方法本身。

## 二、第一层：设计闸——不变量先行

### 2.1 不变量注册表（任何功能动工之前）

机器可读（如 `scripts/invariants/registry.ts`），由 CI 自动发现，**不做成文档**——文档会漂，注册表会被守卫校验。每条四要素：

```
id        ：INV-CORE-07（命名空间统一，见 9.3 号段纪律）
statement ：一句话，主语是系统（「每道闸必须有界面入口」）
c7        ：判例引用（本仓台账编号；历史缺陷归并来源）
guard     ：守卫脚本路径（enforced/partial 必填）
badSample ：坏样本描述与位置（enforced 必填，缺了不许标 enforced）
status    ：enforced（守卫+反证+在位）/ partial（缺口必写）/ missing（理由+复审触发器）
```

**状态语义（防改账，照抄）**：
- `enforced` = 判据在 + 注入坏样本必红 + 还原必绿 + 已被 CI 跑到。四者缺一降级。
- `partial` = 有守卫但只覆盖一部分，**缺口字段必填**。
- `missing` = 无守卫，**理由必填 + 必须带复审触发器**（90 天或「相关域出新缺陷即复审」）。**没有触发器的 open 就是换个名字的永久豁免槽。**
- **不设覆盖率阈值。** 设阈值必诱发「为达标把 missing 改成 partial」的改账动机——那是把账本改成成绩单。

**三个动作（别记更多）**：
- **A**｜AI 新写一列忘了接线 → 守卫当场红并点名。处置二选一：补写入者 / 删列。**不许往豁免里塞**——豁免只收「已裁决、暂不修」的账，每条理由 ≥8 字。
- **B**｜新缺陷进来 → 第一问不是「补什么测试」，而是「**它违反了哪条不变量**」：落进已有条目 → 补该守卫的射程（不新开守卫）；都没违反 → 新的一类 → 追加 INV，必须同时给守卫或 missing 理由+触发器。
- **C**｜要动 schema/迁移（不可逆）→ 先答「呈批五问」（附录 C-2），答不全不进实施队列。

### 2.2 方向裁决纪律

发现「规范说 X、代码没有」（或反之）时，**强制二选一：规范错 → 改规范；代码错 → 改代码。禁「两边都对」**——和稀泥把一个真分歧变成两个假一致，而假一致会在飞检/审计/对账时被当成两个真事实。

### 2.3 承诺必有抛错点

规范、注释、界面文案里每句「系统会做 X」，要么有一个抛错点/写点/路由给它背书，要么删句。**界面承诺的力 = 服务端的力**：界面说的比服务端弱（弱化的提示词）或强（承诺不存在的按钮）都是缺陷。

### 2.4 设计闸检查清单

- [ ] 本功能依赖的不变量已在注册表？没有 → 先立项 INV
- [ ] 每条 enforced 有坏样本且注入记录留档？
- [ ] 每条 missing/partial 有理由 + 复审触发器？
- [ ] 本次改动涉及的「承诺句」逐句有背书或已删？

## 三、第二层：架构闸——让「两边一起缺」不可能

### 3.1 四条架构铁律

1. **一张表一个 owner 模块。** 跨模块只准经 service 层，禁跨模块直连业务表。owner 负责该表的全部字段、约束、守卫。
2. **依赖方向单向**：呈现 → 领域 → 数据。禁反向回指（呈现层不准定义领域规则，领域层不准引用呈现组件）。
3. **不变量住在它最便宜的层**：租户隔离住 DB（RLS），状态机住类型+守卫，业务判据住注册表，文案住词表单源。**能下沉的决不上浮**——上浮一层，检测成本 ×5。
4. **每个跨模块契约登记 owner**：错误码域、枚举域、状态机域、契约域各有唯一真源。AI 不知道两条规则同出一个 owner，只有登记了它才不会各写一遍（附录 B-10 判例：册↔码文案各漂数十处）。

### 3.2 场景洞位图（骨架相同，装填不同）

| 洞位 | 交易密集型系统 | 审批/审计密集型系统 |
|---|---|---|
| 并发与资金 | 超卖、回调重复、定价多套 | 序号取号冲突、审计链序号竞态 |
| 审计与追溯 | 操作日志、实体变更轨迹 | 字段级审计+哈希链、签名绑快照 |
| 状态机 | 申请/审批/履约 | 多级复核链、放行冻结 |
| 不可逆 | 删除/不可逆审批 | 迁移链、销毁、枚举加值 |
| 合规口径 | 宣传词/标价 | 判据措辞、场景化限值 |

**架构评审只问一句：这个设计里，「两边一起缺」发生在哪条缝？** 答不出 = 还没想完。

### 3.3 架构闸检查清单

- [ ] 每张表能一指说出 owner 模块？
- [ ] 依赖图无环、无反向边？
- [ ] 每条系统级不变量能说出它住在哪层、为什么那层最便宜？
- [ ] 每个跨域概念（错误码/枚举/状态）有唯一真源登记？

## 四、第三层：栈闸——选「能约束 AI」的技术

### 4.1 四条选型判据（按权重排序）

| 判据 | 为什么 | 反例 |
|---|---|---|
| **① 约束表达能力** | 让非法状态不可表达 = AI 的合理默认值变类型错误 | 需要手写校验一切的「灵活」框架 |
| **② 静态可分析性** | 守卫靠 grep/AST 吃饭；魔法越多判据越假 | 运行时动态表名、字符串拼 ORM 条件 |
| **③ 可重放性** | 不可逆操作要有免费试错通道 | 迁移外置手工步骤（带外 SQL 的教训） |
| **④ 单源可生成** | 边界能生成代码，AI 才只填中间 | 每处手写校验函数（150 个 route 手敲 typeof） |

参考落地：PostgreSQL（RLS/枚举/FK/触发器/ advisory lock）、TypeScript 判别联合、Prisma + 手写迁移、zod 边界校验。

### 4.2 边界零手写验收线

**「AI 填中间、不碰边界」的前提是边界真实存在且是生成的。** 栈闸的硬验收线：

```
schema.prisma ──生成──▶ TS 类型 ──生成──▶ zod 校验 ──生成──▶ 表单骨架/契约文档
                                    │
                                    └── 手写校验函数只允许在生成器内部
```

- 新增 route 的输入校验**来自生成**，禁止 `req.json() as X`、禁止逐字段手写 `typeof`；
- 新增枚举**来自一处定义**，守卫与迁移由它派生；
- 边界文件清单进守卫：扫描到生成区出现手写校验即红。

### 4.3 栈闸检查清单

- [ ] 每类边界（输入/枚举/错误码/契约）能一指说出它的生成源？
- [ ] 全仓 grep 手写校验函数的数量在收敛（有基线读数）？
- [ ] 迁移链无带外步骤，干净库可整套重放？
- [ ] 数据库用了约束表达能力（RLS/枚举/唯一索引），而非「应用层自觉」？

## 五、第四层：规范闸——规范即生成源

### 5.1 模块规范四件套（缺一即未交付）

1. **字段清单**：每列标注 `写入者（函数名）/ 读取者 / 存档声明`。这是「列有写入者」不变量的册面形态——**缺「写入者」列的字段清单不予评审**。
2. **状态机**：枚举值 + 合法跃迁 + **每个值的产生路径**（哪个写点、什么条件）。产生路径写不出的枚举值 = 死枚举，当场裁决（删值或补写点）。
3. **判据**：闸、拦截清单、时限——**每条带拒收句**，拒收句反过来 grep 界面控件（没有控件的拒收句 = 空转闸，附录 B-1）。
4. **验收用例**：可直接转守卫/e2e 的判定表。

### 5.2 规范互不冲突的机制（四件套之外的元纪律）

- **单一真源（D1）**：一条规则只有一个 owner 册；其余册只准写指针句（「真源见 X §N」），**禁复述正文**。复述必然漂移——别追，消灭产生漂移的结构。
- **变更五步流程**：① 提案（写进发起册修订记录）→ ② 台账登记 → ③ 受影响册同批同步 → ④ 判据全绿 → ⑤ 版本号四处落位。**禁「回头再对齐」**。
- **号段归属总表**：每套编号（错误码/用例/不变量/验收）登记唯一 owner；**新增先查占用**（两趟 grep：在册 + 在途自称）。
- **机器判据化**：凡被扫到两次以上的原则，必须有一个地址（守卫或注册表）——「注释里的纪律等于没有纪律」。

### 5.3 规范闸检查清单

- [ ] 本模块四件套齐？字段清单的「写入者」列填了？
- [ ] 每个枚举值有产生路径？
- [ ] 每条判据有拒收句，拒收句 grep 得到控件？
- [ ] 本文档无复述他册规则（过复述扫描）？
- [ ] 变更走了五步，受影响册同批？

## 六、第五层：测试闸——测性质，不枚举路径

### 6.1 三层金字塔（价值配比 70/25/5）

| 层 | 验什么 | 占比 | 铁律 |
|---|---|---|---|
| **不变量守卫** | 一类缺陷恒不成立 | 70% | 三态齐全（见 6.2），坏样本独立注入 |
| **e2e 冒烟** | 主链路走得通 | 25% | 守卫挡住的东西不重复验；桩随闸走 |
| **人工抽检** | 语义/视觉/盲区 | 5% | 盲区登记在册，不假装没有 |

**e2e 唯一的增值是「闸落地后用例跟上」**：服务端加必填闸，消费面（含小程序/离线队列 payload）必须同批普查——Web 改完 ≠ 全端改完。

### 6.2 守卫三态（缺一不算守卫）

1. **建成**：判据代码存在且能运行。——什么都不证明。
2. **反证**：注入已知坏样本**必须见红**，撤掉后**必须复绿**。记录留档（坏样本内容 + 红读数 + 绿读数）。**判据：校验脚本报假绿比不报更危险。**
3. **在位**：被 CI/跑批自动执行，退出码参与结论。

**守卫自证三件套（防「守卫自己坏掉」）**：
- 解析到 0 个对象 → 抛错，**禁止把「读到 0 个」当「没有问题」**；
- 比对基准必须能对上（schema 的 key 与库表名对上率自检，对不上即抛）；
- 输出**自报口径**（「扫了哪些目录、排除了谁、为什么」），排除也必须留痕。

### 6.3 坏样本三纪律

1. **独立注入**：坏样本由对账方从不变量反面构造，**禁止实现者自造**（守卫自己造数测自己的闸 = 永绿）。
2. **一条判据一个坏样本**：注入必红、还原必绿，两个方向都要记录。
3. **反证即资产**：坏样本固化进守卫（`--self-test` 或 fixture），每次跑批重放。

### 6.4 假红与假绿同罪

- **假绿**放过缺陷，且让人以为已验证（读到 0 个对象报绿、范围落后现实静默放行）。
- **假红**消耗信任，且让人去「修」没坏的东西——**一个报 33 个问题的守卫，第一反应应是「守卫错了」而不是「代码有 33 个问题」**（差点把已停用功能当死代码删掉的判例）。
- 配套：**带时间窗的夹具禁止硬编绝对日期**（曾经真绿的断言会随日历变红，比永真断言更难发现）。

### 6.5 测试闸检查清单

- [ ] 每条守卫有反证记录（坏样本 + 红读数 + 绿读数）？
- [ ] 每条守卫自报扫描范围与排除理由？
- [ ] e2e 桩随服务端新闸同批改？
- [ ] 人工抽检的盲区登记在册（而非「测试通过」一句话）？
- [ ] 跑批退出码取被测物自己的（`pipefail`/`PIPESTATUS`）？

## 七、AI 协作协议（五条规定）

1. **AI 填中间，不碰边界。** 边界（schema、契约、枚举、错误码、状态机）由单源生成；AI 只写中间业务逻辑。边界还是手写的系统，这条不成立——先补第三层。
2. **先出「哪里会静默出错」清单再动手。** 让 AI 对每个功能先列「可能静默失败/假绿/无来源」的点，再实现。它对「哪里会假绿」的敏感度远高于「功能做对没有」。
3. **坏样本由对账方注入**（6.3），AI 自测结果不单独采信。
4. **产出验收顺序固定**：不变量查表（违反第几条 INV？）→ 守卫 → e2e → 人工抽检。**先查表后跑测**——查表是秒级，跑测是分钟级。
5. **AI 的每个「已完成」声明必须可寻址**：commit、守卫读数、或台账行，三者至少一。「已完成」三个字不构成证据。

## 八、不变量库

### 8.1 通用骨架 INV-CORE-01～15（两仓实测归并，照抄起步）

| # | 不变量 | 判据形态 |
|---|---|---|
| 01 | 每一列要么有写入者，要么不存在 | service 写点静态扫描 + 「读不算写」判别 |
| 02 | 每一列要么有读取者，要么声明为存档 | schema 注释约定 + 读点扫描 |
| 03 | 枚举每个取值至少有一个产生路径 | 枚举↔列↔写入上下文反查 |
| 04 | 状态判据只允许一份（副本即红） | 状态字符串字面量唯一源扫描 |
| 05 | 软删表的一切读带过滤（含按 id 读、计数、导出、趋势） | 读点全家桶静态扫 + 坏样本 |
| 06 | 规范/注释每句「会做 X」必有抛错点或挂账 | 承诺句清单 ⇄ 抛错点 grep |
| 07 | 每道闸有界面入口，每句拒收词有控件应答 | 拒收句档位词 ⇄ 控件 grep（反向走闸） |
| 08 | 多租户一切写带租户谓词；身份/豁免表也在射程 | 写口静态扫 + 事务内判定 |
| 09 | 迁移链在干净副本库可整套重放且对象零漂移 | fresh-copy deploy 对拍 |
| 10 | 新码先登记、在用码必有抛错点；契约三面（册/码/提交体）机器对拍 | 注册表 ⇄ 代码双向 diff |
| 11 | 资金恒等式逐笔成立；冗余计数可从源表重算 | 探针对账 + 重算一致性 |
| 12 | 写路径不得 check-then-act；并发热点有锁与冲突分类 | 模式扫描 + 并发探针 |
| 13 | 守卫在册必须被跑到（有入口）且自证射程 | 注册表校验（本手册的 meta 守卫） |
| 14 | HEAD 从干净检出可构建；关键件全部入库 | 干净 worktree 编译探针 |
| 15 | 机制存在 ≠ 生效：声明位/模板/守卫启用率 >0 才可宣称交付 | 启用率读数（INFO 永驻） |

### 8.2 场景包 A：交易密集型系统（在骨架上追加）

- 余额扣减必须 CAS（`WHERE balance >= ?`），禁 read-then-write
- 外部回调全链路幂等键，重复通知不产生第二条记录
- 金额以服务端账本为准，客户端金额仅展示
- 数值单源计算，禁前端套二次调整
- 一次性凭据核销并发原子，过期判定用服务端时钟
- 热点序列（业务序号/凭据号）advisory lock 或序列表，禁 max+1

### 8.3 场景包 B：审批/审计密集型系统（在骨架上追加）

- 字段级审计 append-only：DB 触发器 + 应用守卫 + 权限回收三层
- 签名绑签署时刻快照，校验用快照重算不读活行
- 复核四眼服务端硬拒：同人自复核、同人双签、顺序颠倒全部 4xx
- 放行冻结未解除，批准动作服务端不可达（不是按钮置灰）
- 枚举产生路径逐一登记；死枚举当场裁决
- 不可逆操作（迁移/销毁/枚举加值）呈批五问 + 干净库重放
- 离线补签可见：`offline` 标记 + 延迟时长常驻，L3 级禁离线
- 「机制存在 ≠ 生效」列入每批收尾读数

### 8.4 新不变量立项格式（一句话 + 四要素，缺一不立）

```
INV-XX：<系统恒成立的一句话，主语是系统>
c7     ：归并来源（历史缺陷编号）
guard  ：判据形态（怎么机器验）
bad    ：坏样本怎么造、注入后期望哪条红
```

**立项前自检**：这句话能用「存在/任意/恒不」表述吗？不能 → 它只是用例，不是不变量。

## 九、治理机制

### 9.1 台账五纪律（防账本 itself 腐烂）

1. **计数可复现**：每条带计数的结论附复现命令；命令是真源，册面数字只是带日期的快照。**复现命令与登记不符即红。**
2. **锚点禁行号**：登记用「册 + 表名/节号」，不用行号（行号随编辑漂移，错锚比无锚更危险）。
3. **open 带触发器**：理由之外必须有复审触发条件，到点未处理转红。
4. **登记 ≠ 处置**：挂账必须同时写明销项条件，否则只是把缺陷搬了个地方。
5. **让号双趟 grep**：取号前 grep 在册 + 在途自称（代码注释先占号会造成两批同号的假对账）。

### 9.2 批次纪律

- **先裁后建**：方向裁决（改册/改码）先于施工；裁前不写了代码再补账。
- **先红后绿**：新守卫上线第一天必须对一个已知坏样本见红。
- **收尾对账**：每批交付前，本批触及的实体字段/枚举/号段与 schema 逐一核对；结论是「零分歧」也要把这句话写进批记录——**没写 = 该批未收尾**。
- **排期 ≠ 完成**：未 commit 的「✅」一律标注「排期声明」，完成读数以 commit + 守卫读数为准。
- **收尾必查两件**：`tsc` 现值复跑（别引用上一轮的读数）；并行批红逐条分型（非本批不代改，但要说清是谁的）。

### 9.3 变更五步流程（改任何规则的必经之路）

提案（发起册）→ 台账登记 → 受影响面同批同步 → 判据全绿 → 版本四处落位。中途任何一步跳过，等于没改。

## 十、落地路线图

### 10.1 第 0 步：现有系统体检（半天，十问）

1. 有没有不变量注册表？没有 → 第一周先立（第八章照抄起步）
2. 守卫有多少、多少有反证记录？抽查 5 个，注入坏样本看红不红
3. 有没有「在盘无入口」的守卫/脚本？（package.json 双向 diff 一遍）
4. schema 里有多少零写入列？（写点扫描，基线读数）
5. 枚举有多少值无产生路径？
6. 迁移链能否干净库整套重放？
7. 边界（输入校验/枚举/错误码）是生成的还是手写的？手写比例基线
8. 软删表读点是否全带过滤（含按 id 读）？
9. HEAD 干净检出能否构建？
10. 最近的 10 个缺陷，各违反哪条不变量？（归并度检验——多数应落进已有条目）

### 10.2 四周计划

| 周 | 动作 | 产出 |
|---|---|---|
| 1 | 立注册表（骨架 15 条照抄）+ 存量守卫反证审计（5 条抽查注入坏样本）+ 孤儿脚本扫描 | 假绿/假红清单（第一批真实读数） |
| 2 | 消第一批红（方向裁决制）+ INV-13 反向对拍 + 零写列处置（先 raw SQL 扫描、再数据量读数、后裁决） | 注册表首个全绿区间 |
| 3 | 边界生成器（schema→zod→表单，先覆盖写库/资金/权限三类） | 边界零手写第一块 |
| 4 | 模块规范四件套补齐（先补「写入者」列）+ open 条目触发器 + 呈批五问进 PR 模板 | 规范即生成源的第一本 |

### 10.3 稳定态与度量

- **稳定态 = 20～30 条不变量**。新增缺陷多数落进已有条目（查表动作），少数开新条目。**「一次性挖到底」不是「以后不用挖」，是让每次挖掘都沉淀成一条不变量。**
- 三个健康指标：新缺陷落旧条目率（↑）、守卫反证覆盖率（=100%）、零写列/幽灵码计数（→0 并钉住）。

### C-2 呈批五问（动 schema/迁移前，答不全不进实施队列）

1. 新表/新列进 RLS 与软删名单了吗？（豁免也是裁决，不是默认）
2. 每一列的写入者是谁（函数名）？读点在哪？都没有 → 为什么存在？
3. 哪条 INV 守它？守不住的话 openReason + 复审触发器是什么？
4. FK 的级联方向是删除方还是保留方？谁依赖这个方向？
5. 回滚故事：已上线后如何撤回？回滚丢什么数据？（干净库重放读数即本问的兑现）

### C-3 批次收尾清单

- [ ] 方向裁决记录在册（改册/改码，无和稀泥）
